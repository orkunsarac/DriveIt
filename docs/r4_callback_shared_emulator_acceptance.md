# Android callback acceptance — isolated emulator

The app and isolated probe use the same `OwnerAuthLinkListener` composition, including `app_links` stream, initial link, latest link, duplicate handling and `OwnerAuthCallbackDelivery`. The probe is guarded by the isolated test build define and exact isolated package name; it displays only synthetic count and owner labels. It uses real Supabase SDK with synthetic HTTP and a synthetic owner store. It does not initialize production Auth.

API 36 emulator-5554, package `com.example.driveit_project.isolated_test`, standalone debug APK: process-cold `am start -W` returned `LaunchState: COLD`; after the test deliberately delayed listener attachment, UI reported `PASS count=1 owner=A`. Separate process start without a link reported `READY count=0 owner=guest`; a warm VIEW intent was delivered to the top activity and UI reported `PASS count=1 owner=A`. Repeating the same warm intent retained that displayed result. Existing Flutter test checks delivery deduplication directly. A synthetic GPS-busy scenario displayed `REJECT count=0 owner=guest`; a synthetic HTTP 400 exchange displayed `REJECT count=1 owner=guest`. The GPS scenario is a simulated busy predicate, not a physical GPS/journal acceptance. No actual email, user account, production service or physical phone was used.

Targeted Flutter callback/owner/SDK tests 48 PASS; changed sources analyzed with no issues. The probe is a debug test artifact, not a production activation. Play Auth remains closed. The production entry point delegates to the shared listener, but the Play package and end-to-end production composition were not enabled or tested. Session restore, controlled refresh and real recovery remain separate incomplete work.
